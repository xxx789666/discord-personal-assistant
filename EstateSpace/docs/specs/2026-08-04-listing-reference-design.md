# 銷售中物件參照 + 實價登錄改 2 年 — 設計

日期：2026-08-04
狀態：設計已確認，待實作
影響頻道：`#不動產估價`（`openab-estate` / EstateSpace）

## 1. 背景與目標

目前估價只有單一資料來源：內政部實價登錄（`tools/lvr.py`）。它反映**過去的真實成交**，
但有登錄時間差，抓不到當下的市場要價。

本次新增第二個參照：**附近銷售中物件的開價，扣除議價空間後**，與實價登錄並用。
兩者性質互補 —— 成交是事實但落後，開價即時但含賣方意圖。

同時把實價登錄的預設查詢年限從 3 年縮短為 2 年，讓比價基準更貼近當前行情。

## 2. 範圍

**做**

- 新增 `EstateSpace/tools/listing.py`：查詢銷售中物件、折算議價空間、輸出統計
- `tools/lvr.py` 預設年限 3 → 2，並同步 `WebAccess.md`、`AGENTS.md`
- `AGENTS.md` 新增 §銷售中參照 方法論與回覆格式
- parser 與折算/統計函式的 fixture 單元測試

**不做**

- 不修改 `property-case-radar` 專案
- 不連它的資料庫、不接它的 compose 網路、不引用它的套件
- 不處理它排程 misfire 漏跑的問題（另案）
- 不實作 591 來源（Radar 的 591 路徑需要 operator 手動執行 Playwright capture，不屬於本次「每次估價現爬」的模式）

## 3. 關鍵決策與理由

### 3.1 複製腳本，不串接 Radar

`property-case-radar` 的 main 分支已有完整銷售中管線（`HousefunSaleCrawler`、
`CapturedSaleCrawler`、`CompositeSaleCrawler`、`sale_pipeline`），並提供唯讀的
agent 查詢介面 `tools/radar_agent_query.py house-search`。

**仍決定複製而非串接**，理由：

- 兩套系統維持獨立，不建立跨 compose 專案的網路與憑證依賴
- Radar 的本機部署落後遠端（映像建於 2026-07-24 的 `049a3de`，遠端已到 `87ba421`），
  其 `properties` 表目前 0 筆；串接會讓估價頻道的可用性綁在另一個專案的部署進度上
- `HousefunSaleCrawler` 是無地區參數的 bounded adapter（只抓首頁與 `?pg=2..3`），
  本來就無法直接滿足「查標的附近」，複製後仍需改寫

複製的價值在於**沿用它已驗證的合規行為**，不在於重用程式碼。

### 3.2 議價空間：預設固定值，可單次覆寫

預設 **8%**，寫進 `AGENTS.md`。使用者可用一句話覆寫（「這區議價空間約 12%」），
工具端以 `--discount 0.12` 傳入。**回覆一律註明實際採用的百分比。**

不採分級表：分級依據是經驗值、難查證，且會讓規則複雜化。
不採不折算並列：使用者要的是可直接比較的單一參照值。

### 3.3 併用方式：實價登錄為主，銷售中為輔

估價金額**仍由實價登錄成交中位數決定**；折後開價只做交叉驗證。

理由：成交是事實，開價是意圖，且折後值多帶一層議價空間假設。
兩者等權（加權平均）等於在假設上疊假設，且回覆難以複核，違反工作區
「計算務必逐步透明」與「絕不憑臆測報數字」的既有原則。

**土地例外**：土地 SOP 本來就報區間，折後開價可參與區間上緣認定。

## 4. 元件：`EstateSpace/tools/listing.py`

### 4.1 形態

比照 `tools/lvr.py`：PEP 723 inline script metadata、`uv run` 執行、CLI 介面、
純文字輸出給 agent 讀。相依：`httpx`、`beautifulsoup4`、`truststore`。

容器內沒有 `curl` / `python3`，一律 `uv run`。

### 4.2 介面

```bash
uv run tools/listing.py --city 桃園市 --district 桃園區 --road 永安路 --type 透天
uv run tools/listing.py --city 桃園市 --district 平鎮區 --land --discount 0.12
```

| 參數 | 說明 |
|---|---|
| `--city` | 必填，縣市。**唯一進入請求 URL 的地理參數** |
| `--district` | 必填，鄉鎮市區。**回傳後對地址篩選**（見 4.3） |
| `--road` | 選填，回傳後對地址篩選；預期常為 0 筆，自動回退到區級 |
| `--type` | 選填，型態關鍵字（透天／公寓／華廈／住宅大樓） |
| `--land` | 土地模式 |
| `--discount` | 議價空間，預設 `0.08` |
| `--limit` | 輸出筆數上限 |
| `--max-pages` | 抓取頁數上限，預設 3、硬上限 3 |

### 4.3 合規行為（不可省略）

自 Radar `crawlers/sale/housefun_source.py` 沿用：

- 每次執行**先抓 `robots.txt`**，以 `urllib.robotparser.RobotFileParser` 驗證目標路徑
- User-Agent 標明來源與用途，**不偽裝瀏覽器**
- 請求間隔 ≥ 2 秒
- 頁數上限 3

**SSL**：容器內必須用 `truststore.SSLContext(ssl.PROTOCOL_TLS_CLIENT)`。
直接用 httpx 預設會失敗於
`CERTIFICATE_VERIFY_FAILED: Missing Subject Key Identifier`（2026-08-04 實測）。

額外限制（2026-08-04 實測 `https://buy.housefun.com.tw/robots.txt` 得出）：

該站 robots.txt 只宣告 `User-Agent: OAI-SearchBot` 一個 group（沒有 `*`），
內容為 `Allow: /` 加四條 `Disallow`，其中兩條是
`/Building/building_street*` 與 `/building/building_street*`。
嚴格說那些規則不適用於本工具的 UA，但仍**照樣遵守** —— 那是站方對該路徑表達的意圖。

### 4.4 只能查到城市級（spike 結論）

實測四種地區 URL 格式：

```
/region/桃園市桃園區_c/   → 回台北市物件（中正/萬華/松山/士林/內湖）  ← 靜默回退
/region/桃園市_c/        → 回桃園市物件（中壢/桃園/龜山/大園/蘆竹）  ← 正確
/region/桃園市桃園區/     → 同樣靜默回退到台北市
```

**未知的地區 slug 不回 404，而是靜默回退到台北市的預設頁。**
城市頁自己產生的 27 個 `/region/` 連結全是排序（`?od=`）與分頁（`?pg=`），
沒有任何區級連結；頁面也沒有區選單，「桃園區」只出現在 `<script>` 與物件地址中。
**區篩選是 JS 驅動的，沒有可安全構造的靜態 URL。**

因此：

- **只有 `--city` 進入請求 URL**；`--district`、`--road`、`--type` 全部是客戶端篩選
- **必要防護**：回傳物件的縣市若與請求不符，**中止並報錯**，不得沉默使用。
  沒有這道防護，一個拼錯的縣市名會讓估價拿台北的物件當桃園的參照且毫無徵兆
- 預期樣本量（3 頁 × 30 = 90 筆全市）：區級約 20 筆（足夠，門檻是 3 筆）、
  路名級 0~2 筆（通常不可用，自動回退到區級並在回覆中說明）

回退到區級與 `lvr.py` 既有的「同路段不足就放寬整區」階梯概念一致。

### 4.4 輸出

每筆：地址、坪數、開價總價、開價單坪、屋齡、型態、來源 URL。

統計兩組：**原始開價**與**折後**的中位數／平均／min／max。

比照 `lvr.py` 做輸出截斷保護 —— NVIDIA NIM 端在 context 過大時會回
EngineCore error / -32603（2026-06-12 實測），輸出必須維持精簡。

## 6. `AGENTS.md` 新增 §銷售中參照

- **時機**：每次估價，在實價登錄查詢之後執行
- **折算**：`折後單價 = 開價單價 × (1 − 議價空間)`
- **併用**：估價基準仍為實價登錄成交中位數；折後開價做交叉驗證
- **落差示警**：`|折後開價中位數 − 成交中位數| ÷ 成交中位數 > 15%` 時，
  在回覆中示警並列出可能原因（屋主開價偏高／近期行情變動／樣本型態不一致）
- **土地**：折後開價可參與估價區間上緣
- **查不到**：明確寫「本次無銷售中參照」，估價照常以實價登錄進行，**不阻斷流程**

## 7. 回覆格式

於既有骨架新增一段：

```
【銷售中參照】桃園區永安路周邊，3 筆在售：
  ・永安路 xxx 號 透天 68.5 萬/坪（開價）→ 63.0 萬/坪（折 8%）
  ・…
  → 折後中位數：63.0 萬/坪
  ⚠ 與成交中位數 64.2 萬/坪 差 1.9%，一致
```

免責聲明併入既有那句，額外註明開價已折算及所用百分比。

## 8. 失敗處理

| 情況 | 行為 |
|---|---|
| robots.txt 抓不到或禁止目標路徑 | 中止查詢、回報使用者、**不繼續嘗試**；估價僅用實價登錄 |
| 頁面解析不到任何物件 | 視同無資料，回覆「本次無銷售中參照」 |
| 網路逾時 | 不重試超過 2 次；失敗即視同無資料 |
| 折後樣本 < 3 筆 | 仍可列出，但標註「樣本不足、僅供參考」，不納入落差示警判斷 |

任何情況下**都不阻斷估價**——實價登錄是主線，銷售中是加分項。

## 9. 測試

EstateSpace 目前無測試。本次新增最小集合：

- **parser**：存一份好房網列表頁 HTML 作 fixture，測欄位抽取正確性（最易因改版而壞）
- **折算**：`開價 × (1 − discount)` 的邊界（discount=0、極端值）
- **統計**：中位數／平均在偶數筆、單筆、空集合下的行為
- **不測**網路請求與 robots 抓取（屬整合行為，靠實跑驗證）
